# iOS helper feasibility — Phase 0 task 0.10

Checked: **2026-11-01**. Research only; no Mac/iPhone build, benchmark, sandbox test or App Review decision was obtained. Each source reference below includes its check date. Decisions are project recommendations inferred from the cited constraints, not Apple approval.

## Interpreter feasibility (technical gate)

| Candidate | Evidence and assessment |
|---|---|
| Wasmtime Pulley | A no-native-JIT execution path is technically plausible: Pulley interprets its own bytecode, produced by Cranelift. Enable the `pulley` feature and explicitly select `pulley64` for a 64-bit little-endian host; ARM64's default native backend must not be mistaken for interpreter mode. Upstream expects roughly an order-of-magnitude (~10x) slowdown versus native/Cranelift, not an iPhone benchmark. [Portable Interpretation](https://docs.wasmtime.dev/examples-pulley.html) (checked 2026-11-01). |
| Wasmtime on iOS | iOS is supported but less tested than primary desktop OSes. Native Cranelift/Winch execution requires executable memory pages; merely switching native compilation from JIT to AOT does not establish iOS compatibility. Pulley is the candidate to spike. Actual current iPhone compatibility, peak resident memory and linked binary size are **unknown** in this research; no iOS figures are supplied by this source. [Platform support](https://docs.wasmtime.dev/stability-platform-support.html) (checked 2026-11-01). |
| WAMR interpreter | WAMR offers interpreter modes separately from AOT/JIT. Current README lists ~58.9K fast-interpreter and ~56.3K classic-interpreter **core-vmlib text on Cortex-M4F**, not iOS app sizes. iOS is absent from its current platform list, so production iOS support is **unknown**. [WAMR README](https://github.com/wasm-micro-runtime/wasm-micro-runtime/blob/main/README.md) (checked 2026-11-01). An upstream issue records interpreter success on iPhone 8/iOS 13.3.1 in 2020; that is historical evidence only, not current validation. [Issue 242](https://github.com/bytecodealliance/wasm-micro-runtime/issues/242) (checked 2026-11-01). |
| wasm3 | Current iOS support, no-JIT configuration, maintenance status, memory and binary size: **unknown within the permitted source set**. Neither Apple nor the runtime sources cited here establish wasm3 feasibility. Do not select it on the basis of this document. [Source boundary: Apple software requirements](https://developer.apple.com/app-store/review/guidelines/#software-requirements) (checked 2026-11-01; does not certify individual interpreters). |

WAMR exposes separate runtime heap, operand stack and linear-memory controls; linear memory contains data, auxiliary stack and heap. Its memory guide documents allocator choices and tuning rather than an iOS memory budget. iPhone peak RSS, safe memory cap, thermal behaviour, sustained throughput and final signed app size remain **unknown**. [WAMR memory model](https://github.com/wasm-micro-runtime/wasm-micro-runtime/blob/main/doc/memory_tune.md) (checked 2026-11-01).

Recommended experiment, not a completed result: compile interpreter-only builds, verify no runtime native-code generation, run bundled deterministic fixtures on a physical phone, measure stripped archive/app size and peak RSS, and test Stop, infinite loops, memory growth and expiration. No alternative runtime is accepted until the project's required containment and one-second Stop can be demonstrated; no isolation waiver is proposed.

## App Store gate

Guideline 2.5.2 requires bundle containment and prohibits downloaded/installed/executed code that introduces or changes app features or functionality. Its limited educational-code exception requires viewable/editable source and is not a general compute exception. **Inference:** downloaded arbitrary Wasm jobs have no established permission merely because they are interpreted. Guideline 4.7 permits specified nonembedded software categories, with further responsibilities; it does not explicitly authorize this distributed Wasm helper. Eligibility under 4.7 is **unknown** and needs Apple review. [App Review Guidelines, 2.5.2 and 4.7](https://developer.apple.com/app-store/review/guidelines/) (checked 2026-11-01).

**Recommendation:** bundle a fixed kernel catalogue in the submitted app, disclose every kernel to reviewers, and download data only. That removes the downloaded-functionality concern but does not guarantee approval. Background services must serve their intended purposes (2.5.4); avoid excessive resource use/heat (2.4.2), hidden functionality (2.5.19), and on-device cryptocurrency mining (3.1.5(ii)). General third-party compute acceptance is **unknown**. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) (checked 2026-11-01).

## Background execution

| Mechanism | Start, work and duration | Interruption / implication |
|---|---|---|
| `BGContinuedProcessingTask` (iOS 26) | Explicit user action in foreground; a finite, understandable goal with measurable progress. Can continue CPU/network work after backgrounding; Apple describes minutes or more, without a fixed guaranteed maximum. Submit a request; queue when constrained or select fail-if-unavailable. [Long-running tasks](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/) (checked 2026-11-01). | Report progress and complete the task; user cancellation calls expiration handler. Resource constraints can terminate work, prioritizing tasks with poor progress. Stop promptly on expiration. Same source (checked 2026-11-01). |
| Continued-task intent | A prior preference is not authorization for automatic launches; tasks must follow an explicit action and have a clear completion goal. iOS can throttle, suspend or terminate costly background work. **Inference:** an endless “help whenever jobs arrive” queue is a poor fit. [WWDC25: Finish tasks in the background](https://developer.apple.com/videos/play/wwdc2025/227/) (checked 2026-11-01). | No promise of an overnight window or uninterrupted session. Exact runtime on the owner's devices: **unknown**. Same source (checked 2026-11-01). |
| `BGProcessingTask` | System-scheduled deferred processing, not immediate dispatch. Register at launch and submit a request; request can require external power/network. Runs for minutes while idle. [Task](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask), [request](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtaskrequest), [scheduling explanation](https://developer.apple.com/videos/play/wwdc2022/10083/) (checked 2026-11-01). | System can interrupt; user activity terminates processing tasks. Implement expiration cleanup and enable `processing` background mode. No exact start-time or whole-night guarantee. [Task](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask) (checked 2026-11-01). |
| Background GPU | Continued processing can use GPU only on supported hardware, with Background GPU Access entitlement enabled and `.gpu` requested after checking `supportedResources`. [Long-running tasks](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/) (checked 2026-11-01). | This is conditional task access, not a persistent GPU daemon. Recommendation: keep GPU outside v1; phone support and measured limits are **unknown**. Same source (checked 2026-11-01). |

## Local networking

Network framework supports connections/listeners and Bonjour discovery; Apple peer-to-peer Wi-Fi is opt-in. MultipeerConnectivity is deprecated (Apple's current migration note identifies Xcode 27); migrate to Network framework. Bonjour discovery does not establish project peer identity. **Recommendation:** mDNS/Bonjour plus authenticated pairing on the LAN first. [TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework) (checked 2026-11-01).

First local-network access prompts the user; include `NSLocalNetworkUsageDescription`, declare browsed Bonjour service types in `NSBonjourServices`, handle denial, and test on hardware (the simulator does not implement local-network privacy). Raw multicast/broadcast has additional entitlement considerations; do not assume a custom Rust mDNS stack has the same requirements as Bonjour APIs. [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) (checked 2026-11-01).

Wi-Fi Aware arrived in iOS 26 on iPhone 12 and later; it supports nearby connectivity without an access point. Use its capability/entitlement and pairing flow, then Network framework. Android interoperability for our protocol is **unknown until tested**, not established by standards support alone. [TN3111](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview), [Wi-Fi Aware](https://developer.apple.com/documentation/wifiaware), [paired connections](https://developer.apple.com/documentation/wifiaware/connecting-paired-devices) (checked 2026-11-01). Apple currently documents that Wi-Fi Aware plus QUIC is unsupported before iOS 27; account for that when targeting iOS 26. [TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework) (checked 2026-11-01).

## Owner prerequisites

- Access to a Mac running a macOS version supported by the chosen Xcode, plus Xcode and the iOS SDK: the supported build environment is macOS, so this Windows checkout alone cannot build/sign the iOS app. Choose the Mac against the live compatibility table rather than buying against a guessed minimum. [Xcode requirements](https://developer.apple.com/xcode/system-requirements/) (checked 2026-11-01).
- Apple Account; free developer registration permits own-device Xcode testing. App Store/TestFlight distribution needs Apple Developer Program membership, **USD 99 per membership year**, local pricing where available; qualifying entities can request fee waivers. [Program](https://developer.apple.com/programs/), [enrollment](https://developer.apple.com/programs/enroll/) (checked 2026-11-01).
- Recommended test equipment: physical iPhone, charging/power measurement setup and LAN peers; validate privacy prompts on-device per [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) (checked 2026-11-01). Hardware cost and owner account eligibility: **unknown**.

## Decisions and recommended v1 scope

| Role | Decision (project inference, checked 2026-11-01) | Conditions / evidence |
|---|---|---|
| (a) iPhone requester/monitor | **GO** | Foreground submit/status UI using Network framework; respect local permission and background suspension. No promise of a continuously connected background monitor. [TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework), [background model](https://developer.apple.com/videos/play/wwdc2025/227/). |
| (b) User-started bounded helper | **GO-WITH-LIMITS** | Research/prototype only until physical-device containment and App Review gates pass. Bundled reviewed kernels, explicit finite batch, progress, cancellation, checkpoint/retry and expiration handling. Downloaded arbitrary kernels excluded. [Guidelines](https://developer.apple.com/app-store/review/guidelines/), [continued tasks](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/). |
| (c) Unattended overnight helper | **NO-GO** | No reliable scheduled whole-night execution guarantee; continued tasks require explicit starts, deferred processing is discretionary and interruptible. [WWDC25](https://developer.apple.com/videos/play/wwdc2025/227/), [BGProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask). |

**Recommended v1:** ship requester/monitor first. Keep bounded bundled-kernel helping behind a separate feasibility/review gate; do not advertise iPhones as dependable overnight capacity. This recommendation follows the dated evidence above; it is not a runtime benchmark or store approval.
